## /czp-naviline-provision Flow

1. Validates the given IP falls in the expected /24 for the region (172.30.12.0/24 use1, 172.29.12.0/24 usw2) — warns only, does not block
2. Auto-refreshes the `foundation` AWS SSO session if expired, for both PALegacyCzp and PALegacySharedServices — no manual login needed
3. Launches the client EC2 in **PALegacyCzp** (797320052894) from the region's golden launch template with the reserved IP and the 4 documented tags
4. Polls SSM every 30s until the instance appears (5–10 min typical)
5. Renames and domain-joins using the same **three-tier approach** as `/commdev-ssrs-provision` (see below) — fully automated, no RDP needed unless all tiers fail
6. Confirms domain join via `Get-WmiObject Win32_ComputerSystem`
7. Runs `Set-CzpNavilineAdConfig.ps1` on the aspgov.pri DC via WinRM PSSession as `svc-czp-navi-prov` — idempotent OU move + group membership
8. Runs `gpupdate /force` then reboots the client server
9. Prompts whether to create DNS records now (unless `-CreateDns`/`-SkipDns` given) — see "DNS Records" section below
10. Reports summary + DNS results + 2 remaining manual steps: SecureLink entry, Salesforce RFC update — matches `czp-naviline-client-deploy.md` Phase 5 exactly, not automated here (out of scope, confirmed with user)

### Three-Tier Domain Join

Same three-tier pattern used by the CommDev SSRS provisioning skill:

| Tier | Method | When used |
|------|--------|-----------|
| 1 | `Add-Computer -OUPath 'OU=C2G,DC=aspgov,DC=pri'` via SSM | Always tried first |
| 2 | `djoin.exe /machineou 'OU=C2G,DC=aspgov,DC=pri'` offline domain join | If Tier 1 hangs or fails |
| 3 | Manual RDP prompt — script reports failure and exits (does not hang) | If Tier 2 also fails |

The join targets `aspgov.pri/C2G` directly via `-OUPath`/`/machineou` rather than joining to the default Computers container and moving afterward — this is least-privilege: the service account only needs join rights scoped to that one OU, not domain-wide. `Set-CzpNavilineAdConfig.ps1`'s `Move-ADObject` step is a safety net in case OU targeting at join time didn't take (e.g. Tier 3 manual join to the wrong OU).

**This is a failure handler, not a step in the happy path** — the user was explicit that every client-deployment run should be fully unattended end-to-end; Tier 3 only fires if both automated tiers fail.

## DNS Records (Step 9)

Added after the initial provisioning build, based on the pattern in `runbooks/legacy-server-decommission.md` (which does the reverse — DNS removal — using the same three DNS systems for legacy decommissions).

**Key discovery from the decommission runbook:** AWS SSM Run Command executing as SYSTEM directly on a DNS host has sufficient local rights to read *and write* DNS records (`Get-DnsServerResourceRecord`/`Add-DnsServerResourceRecordA`/`Add-DnsServerResourceRecordCName` against `-ComputerName 'localhost'`). This means DNS record creation did **not** need a new delegated service account like the AD OU-move/group-membership work did — it reuses the orchestrator's existing `Invoke-SsmCommand` helper directly.

**Confirmed with user:**
- DNS hostname always matches whatever `$ComputerName` the run actually used (P or T) — no special-casing by environment.
- Runs after gpupdate/reboot (Step 9), not interleaved earlier.
- Prompt-gated (`"Create DNS records for $ComputerName now? (Y/n)"`, default Yes) rather than a hard requirement — avoids confusion now that a public IP is also supplied per run. `-CreateDns`/`-SkipDns` switches bypass the prompt.
- Azure auth (`az login`) is checked/handled automatically inside the script (`az account show` → `az login` if needed) — not fully silent like AWS SSO since there's no unattended token refresh path for `az`, but the user isn't bounced to a separate manual command.

### Record types created

| # | Record | Zone/Server | Target |
|---|--------|-------------|--------|
| 1 | Host A | `aspgov.pri`, on the region's DC (same DC as AD config, Step 7) | `<ComputerName>.aspgov.pri` → private IP (`-IPAddress`) |
| 2 | CNAME ×2 | `aspgov.com` internal zone, **always** on `inf-svrdns001` (`i-04d29591f3a1ba9f4`, profile PALegacySharedServices, us-east-1 — fixed, does not vary by client region unlike the DC used for AD/record #1) | `<clientcode>-egov.aspgov.com` and `s-<clientcode>-egov.aspgov.com` (fixed literal `s-` prefix, always both created) → `<ComputerName>.aspgov.pri` |
| 3 | A (public) | Azure DNS, `aspgov.com` zone, subscription `991cd2ea-42a9-40c0-819d-557f37a3ae2b`, resource group `Azure_DNS_RG` (same Azure DNS zone/RG the decommission runbook's Step 8 removes from) | `<clientcode>-egov.aspgov.com` → public IP (`-PublicIPAddress`, prompted separately if not passed and DNS creation proceeds) |

Note: record #1 may already exist by the time this step runs, since `Add-Computer` domain join typically triggers dynamic DNS self-registration in `aspgov.pri` on next boot. The idempotent check-then-create pattern treats "already exists" as success, not an error.

All three record types are idempotent (check-before-create) and every mutating call is gated by `$PSCmdlet.ShouldProcess(...)` — a `-WhatIf` run shows what would be created without touching anything. If the Azure record already exists with a *different* IP than requested, the script warns and asks for explicit confirmation before overwriting (mirrors the decommission runbook's "confirm current value before deleting" caution).

**Status: implemented, not yet exercised against a live client build.** The `az account show`/`az login` non-interactive behavior in particular is unverified in practice — watch this closely on the first real run.

## Lessons Learned — AUGU First Live Build

**Bug found: false "AllTiersFailed" due to PowerShell output-stream leak.** The AUGU run launched the EC2 instance, renamed it, and domain-joined it successfully (confirmed live via SSM: `(Get-WmiObject Win32_ComputerSystem).Domain` returned `aspgov.pri`, correctly placed in `aspgov.pri/C2G`) — but the script reported `AllTiersFailed` and exited before running AD config, gpupdate/reboot, or DNS.

Root cause: inside `Invoke-TieredDomainJoin` in `Invoke-CzpNavilineProvision.ps1`, three calls to `Wait-SsmOnline` were bare statements (not assigned to a variable, not piped to `Out-Null`). `Wait-SsmOnline` does `return $true`. Any unassigned expression inside a PowerShell function leaks into that function's output stream, becoming part of its return value — so `Invoke-TieredDomainJoin`'s actual return was an array like `@($true, 'Tier2-Success')`, not the bare string `'Tier2-Success'`. The check `if ($joinResult -eq 'AllTiersFailed')` then did an element-wise comparison: `$true -eq 'AllTiersFailed'` evaluates to `$true` in PowerShell (the string coerces to boolean, and any non-empty string is truthy), so the comparison spuriously matched and triggered the false failure branch — even though the join had already succeeded.

**Fix:** all four affected `Wait-SsmOnline` calls (three inside `Invoke-TieredDomainJoin`, one at script top-level after Step 3) now pipe to `| Out-Null`. Audited the rest of the script for the same class of bug (any unassigned function call whose function `return`s a value, inside another function) — no other instances found.

**Consequence for AUGU specifically:** the computer is domain-joined and correctly placed in `aspgov.pri/C2G`, but is missing membership in `WSUS_PROD_2AM_GROUP` and `Apply_Schannel_TLS1_2_Enabled` (Step 6 never ran), never had `gpupdate`/reboot applied (Step 7 never ran), and has no DNS records at all — neither the internal aspgov.pri A record, the aspgov.com CNAMEs, nor the public Azure A record (Step 8 never ran).

**Resume capability added:** new `-ExistingInstanceId` parameter skips EC2 launch and the tiered domain join, and goes straight to confirming domain join (as a safety check) then AD config, gpupdate/reboot, and DNS — all of which are idempotent and safe to run against an instance that's already partway through provisioning. This is the general-purpose fix for *any* run that fails or is interrupted after launch/join but before completion, not just the bug above.

**AUGU fix-forward command:**
```powershell
pwsh scripts/czp-naviline/Invoke-CzpNavilineProvision.ps1 -ClientCode AUGU -IPAddress 172.30.12.24 -Region east -Environment Prod -PublicIPAddress 192.88.54.57 -CreateDns -ExistingInstanceId i-0c4400e40b1e97ea2
```

**Second bug found on resume attempt #1: WinRM PSSession loopback hangs.** Step 6 was originally designed to have SYSTEM (via SSM) spin up a WinRM loopback PSSession authenticating as `svc-czp-navi-prov`, then run the AD script *inside* that nested session — copied from the CommDev automation's pattern, which requires `LocalAccountTokenFilterPolicy=1`. On AUGU this hung indefinitely (confirmed via `Get-Process`: 3 orphaned PowerShell processes accumulated across repeated attempts, none making progress, no CPU activity) even after raising the SSM command timeout from 120s to 240s — it wasn't a timing issue, the nested session genuinely never completed.

**Fix:** rewrote Step 6 to authenticate directly with `-Credential` on every AD cmdlet call (`Move-ADObject -Credential`, `Add-ADGroupMember -Credential`, etc.) — the same simple pattern the domain-join step already uses successfully (`Add-Computer -Credential`). `Set-CzpNavilineAdConfig.ps1` now takes a `-Credential` parameter instead of relying on session identity. No PSSession, no WinRM loopback, no LATFP requirement. Removed the LATFP check/set block from the orchestrator entirely.

**Also killed the 3 orphaned processes on inf-svrdc001** via a separate SSM command (`Stop-Process -Force`) before retrying, to avoid resource buildup from repeated failed attempts.

**Third bug found on resume attempt #2, gating gap.** After the credential fix, AD config still failed — this time on a **different** root cause (see "DC Instance IDs" above: wrong DC, missing AWS module) — but gpupdate/reboot ran anyway. Root cause: the gate only checked `$adResult.Status -eq 'Success'`, which SSM reports whenever the PowerShell process finishes running, regardless of whether the script *inside* it threw an error. The AD script's internal error didn't propagate to a non-zero SSM exit, so the gate passed.

**Fix:** AD config now emits an explicit `ADCONFIG_OK` marker only on genuine success (mirrors the `JOIN_OK`/`SCRIPT_UPLOADED` pattern already used elsewhere in the script), and `-ErrorAction Stop` was added to the AD script invocation so a thrown error actually prevents that marker from printing. The gate now checks `$adResult.Output -match 'ADCONFIG_OK'` in addition to `Status -eq 'Success'`.

**Fourth issue found: wrong DC target entirely.** `i-0b420f5e1f69759b7` (inf-svrdc001, use1) and `i-0e5ded06685e7620c` (inf-svrdc011, usw2) — reused from the working CommDev automation — do not host the `aspgov.pri` DNS zone (confirmed via `Get-DnsServerZone`), which broke the internal aspgov.pri A-record check ("zone not found," even though the record already existed elsewhere via dynamic DNS self-registration). Switched to `inf-svrdc101`/`INF-SVRDC111`, which do host the zone and are SSM-online — see "DC Instance IDs" section above.

**Fifth issue: `AWS.Tools.SimpleSystemsManagement` won't load on either corrected DC — wrong fix attempted first.** Initial attempt: since PSGallery isn't reachable from `aspgov.pri` servers (confirmed — `Install-PackageProvider`/`Save-Module` both fail with DNS/connection errors), sideloaded the module by `Save-Module`-ing it on a workstation with internet access, zipping, and copying the folder directly into `C:\Program Files\WindowsPowerShell\Modules\` on the DC. The module then showed up correctly in `Get-Module -ListAvailable` — but `Import-Module` failed: `Could not load file or assembly 'netstandard, Version=2.0.0.0'`. Root cause: these DCs run **.NET Framework 4.6.2** (Release 394802 in `HKLM:\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full`), but AWS.Tools modules require **.NET Framework 4.7.2+** for the `netstandard.dll` compatibility shim. Sideloading the module files doesn't fix a missing runtime dependency — this was a dead end, not a "try again" situation.

**Fix: switched to AWS CLI v2 instead of the PowerShell module.** AWS CLI v2 is a self-contained native binary (bundles its own Python runtime) with no .NET Framework dependency at all, so the version gap doesn't apply. Installed via the standard `AWSCLIV2.msi` (downloaded on a workstation with internet access, copied to the DC via RDP clipboard, installed with `msiexec /i ... /qn`). Confirmed working as SYSTEM via SSM.

**Sixth issue found while verifying the CLI: DC's configured proxy breaks AWS API calls.** First attempt to call `aws.exe ssm get-parameter` as SYSTEM failed with `Failed to connect to proxy URL: "http://172.30.20.55:8080"`. This DC has a machine-wide WinHTTP proxy configured (`netsh winhttp show proxy` confirmed it, no HTTP_PROXY/HTTPS_PROXY env vars were set — it's the WinHTTP system config specifically). `Test-NetConnection` confirmed both the proxy port AND direct HTTPS access to the AWS SSM endpoint are reachable from this DC — so the proxy itself isn't broken/unreachable, it's specifically not correctly proxying this CLI's HTTPS CONNECT/auth handshake. Rather than debug the proxy's AWS-traffic handling, bypassed it entirely for this call (`$env:HTTP_PROXY=''; $env:HTTPS_PROXY=''; $env:NO_PROXY='*'` before invoking `aws.exe`) since direct connectivity already works. Confirmed end-to-end: successfully fetched and decrypted the real 20-character secret value as SYSTEM after the bypass.

**Current script state:** `Invoke-CzpNavilineProvision.ps1`'s Step 6 now shells out to `& 'C:\Program Files\Amazon\AWSCLIV2\aws.exe' ssm get-parameter --with-decryption` (with the proxy bypass env vars set first) instead of `Import-Module AWS.Tools.SimpleSystemsManagement; Get-SSMParameterValue`. This assumes AWS CLI v2 is installed at the default path on every DC this script targets. Now installed on both `inf-svrdc101` and `INF-SVRDC111`.

**Seventh issue, and the actual root cause of the recurring "Missing closing brace" parse error.** After fixing everything above (DC target, credential fetch, gate logic), AD config *still* failed with the exact same phantom parse error we'd seen from the very first resume attempt: `Missing closing '}' in statement block or type definition` at lines 77-79 of `Set-CzpNavilineAdConfig.ps1` — inside the `foreach` loop over `$RequiredGroups`. This had been wrongly attributed to upload corruption earlier in the incident. Direct investigation on the DC: `Get-FileHash` and byte-length of the uploaded file matched the local source file **exactly** — the file was NOT corrupted or truncated in transit. Re-running the direct invocation reproduced the identical error every time, ruling out a transient issue.

Root cause: the script contains UTF-8 multi-byte characters — em-dashes (`—`) inside string literals (e.g. `"Group '$grpName' not found — skipping."`) and box-drawing characters (`─`) in section-header comments. The orchestrator writes the script to the DC via `[System.IO.File]::WriteAllBytes(...)` with **no byte-order-mark**. Windows PowerShell 5.1 (the DC's version, vs. PowerShell 7 on the workstation where this had always parsed fine) falls back to the system's legacy ANSI codepage when a script file has no BOM, rather than assuming UTF-8. On this DC, that codepage misinterprets the multi-byte UTF-8 sequences, and the parser's read position gets desynchronized badly enough to report phantom brace-matching errors several lines later — nowhere near where the actual malformed byte sequence is.

**Fix:** stripped all non-ASCII characters from `Set-CzpNavilineAdConfig.ps1` (em-dashes and comment-header box-drawing replaced with plain ASCII `-`/`--`). Confirmed via a byte-level Python scan that zero non-ASCII bytes remain. Re-ran the AUGU fix-forward command — the AD script now prints its own real internal output for the first time (`Added 'AUGU-PC2GWB001' to 'WSUS_PROD_2AM_GROUP'`, etc.) instead of erroring silently before producing any output at all.

**Final independent verification (not just trusting script output):** fresh `Get-ADGroupMember -Server localhost` query on `inf-svrdc101` after the fix confirmed AUGU-PC2GWB001 is a genuine member of both `WSUS_PROD_2AM_GROUP` and `Apply_Schannel_TLS1_2_Enabled` — `True`/`True`. AUGU is now fully provisioned end-to-end.

**Takeaway for future scripts in this family:** any `.ps1` file that gets written to a target host via raw bytes (`WriteAllBytes`, base64 round-trip, etc.) and then executed by **Windows PowerShell 5.1** (not PowerShell 7) should be kept ASCII-only, or the write step should prepend a UTF-8 BOM (`[byte[]](0xEF,0xBB,0xBF) + $utf8Bytes`) so the legacy parser detects the encoding correctly instead of guessing.

## Added: Windows Activation + RDP Certificate Steps

Two additional steps were added after AUGU's build revealed issues that the runbook didn't originally cover:

**Windows Activation (new Step 6, before AD config):** GPO in this environment later overrides the KMS server setting to `inf-svrkms001.cloud.lcl:1688`, which is unreachable from the CZP subnet — leaving the instance unactivated. The script now activates against AWS KMS (`169.254.169.250`) immediately after domain join is confirmed, before gpupdate can apply the conflicting GPO. Non-fatal on failure — warns and continues, since this doesn't block anything downstream and can be fixed manually later if the watermark returns.

**RDP Certificate (new Step 7, before AD config):** freshly launched instances have no machine certificate bound to the RDP listener, causing NLA errors for hostname-based RDP. The script triggers domain CA auto-enrollment (`certutil -pulse`), polls for up to ~2 minutes for a CA-issued cert to appear, and falls back to generating + binding a self-signed certificate if the CA doesn't issue one in time. Non-fatal on failure — warns and continues (IP-based RDP still works regardless).

Both steps run **unconditionally** after the domain-join-confirmation step, in both the fresh-launch and `-ExistingInstanceId` resume paths — matching how AD config/gpupdate/DNS already work. `$TotalSteps` bumped from 9 to 11; all subsequent `Show-ProvisionProgress` step numbers and `=== Step N ===` banners renumbered accordingly.

**Takeaway for future scripts in this family:** any `.ps1` file that gets written to a target host via raw bytes (`WriteAllBytes`, base64 round-trip, etc.) and then executed by **Windows PowerShell 5.1** (not PowerShell 7) should be kept ASCII-only, or the write step should prepend a UTF-8 BOM (`[byte[]](0xEF,0xBB,0xBF) + $utf8Bytes`) so the legacy parser detects the encoding correctly instead of guessing.
